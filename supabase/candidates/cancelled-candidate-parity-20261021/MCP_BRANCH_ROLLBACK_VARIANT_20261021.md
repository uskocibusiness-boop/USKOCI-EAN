# CCP01 MCP branch rollback proof variant — source only

**Status, 21 October 2026:** [projection.mcp-branch.regression.sql](projection.mcp-branch.regression.sql) was prepared and statically checked. It has **not** been sent to any database. No branch was created, no candidate was applied, and there is no runtime PASS. The original [projection.regression.sql](projection.regression.sql) and [forward.sql](forward.sql) are unchanged.

## Exact target gate

This variant is a **template for one newly identified, data-less, disposable Supabase branch**. It is never a default-project SQL Editor query, a canonical DEV query, or a migration. The MCP call must explicitly use the branch's returned `project_ref`; a branch name or a previously used lab project is insufficient. Do not prepare or send the payload if the branch identity, health, current schema, or candidate application is uncertain.

The source contains three fail-closed placeholders: `__CCP01_BRANCH_PROJECT_REF__`, `__CCP01_BRANCH_SYSTEM_IDENTIFIER__` and `__CCP01_PROOF_NONCE__`. On the branch, read `system_identifier::text` from `pg_catalog.pg_control_system()` through an explicitly branch-targeted **read-only** call. Prepare a *copy* of the SQL by replacing every occurrence of the first two with that branch's returned project ref and the just-read system identifier. Replace the third with a freshly generated lowercase UUID for **this invocation only**; never reuse it. Keep the template unchanged. If the system identifier is unavailable or the branch and its parent have the same identifier, stop; this guard cannot distinguish them.

The SQL's first block rejects an unreplaced or canonical project ref, a system-identifier mismatch, a non-`postgres` SQL role, a non-`postgres` database, any existing Auth/fixture business rows, or a missing/disabled `on_uskoci_auth_user_created` hook. These guards run before fixture inserts. PostgreSQL cannot inspect the MCP request's `project_ref` argument, so the operator must separately verify that argument against the branch record for **every** call. The branch fingerprint and empty-data checks make a misrouted prepared proof fail closed when the two project databases differ.

Read back both candidate function definitions and unchanged public RPC definitions/ACLs after applying `forward.sql` **to that branch only**.
3. Verify the connector's single-call error-stop behavior with an intentional-error probe **on that branch**. Send the entire prepared proof in **one** `execute_sql` call, explicitly targeting the same branch ref used in the SQL template. Do not split the transaction, temp functions, role switches, and final result across requests.
4. Treat only the exact final `PASS CCP01 MCP branch ... fixture rolled back` result, with no tool error, as this projection proof's pass. The final SELECT runs **after** `ROLLBACK`, releases this invocation's session advisory marker placed only after all assertions, and checks that the originally empty Auth and fixture tables are empty again. The marker is drained before any fail-able target check, and the fresh nonce prevents a previous invocation's marker from satisfying this one. Any error, `FAIL`, timeout, unconfirmed rollback, or residue means no proof. Read back branch-local closure/function/ACL state and fixture counts once more as described in the feasibility assessment.

## What changed from the local proof

- The six `auth.users` inserts run with the real Auth insert hook enabled. The proof requires its six `app_accounts` rows and twelve requester/worker profiles, then reads their generated profile IDs. It no longer inserts accounts or profiles a second time.
- For synthetic historical business rows, the proof snapshots user-trigger modes, uses `ALTER TABLE ... DISABLE TRIGGER USER` on the nine public fixture tables, and restores each prior mode before authenticated readers and the real cancellation RPC. It repeats this around the synthetic replacement. Internal foreign-key triggers remain active by PostgreSQL's `USER` semantics ([ALTER TABLE documentation](https://www.postgresql.org/docs/current/sql-altertable.html)).
- The fixture starts with an `ACTIVE` 3/3 need, tests the real cancellation transition to `SELECTION` at 2/3, and marks the synthetic 3/3 replacement `ACTIVE` again. Before replacement, the fourth candidate may never appear `SELECTED` in either owner reader.
- There are no psql meta commands or `SET session_replication_role` statements. The final result is a SQL SELECT after rollback. PostgreSQL documents that session advisory locks survive rollback ([explicit locking documentation](https://www.postgresql.org/docs/current/explicit-locking.html)); the fresh, pre-drained marker prevents a failed assertion followed by a continued final SELECT from producing PASS.

This is still the **3/3 → 2/3 → synthetic 3/3 candidate projection** check. It calls the real cancellation RPC and both owner readers, checks the canceled worker's reader, and checks other-owner/anonymous denial. It does not establish that the real `rpc_select_response` accepts the replacement or that a signed HTTP/Android flow works.

## Static evidence and untested assumptions

Local `pglast` v8.4 parsed the revised 527-line template as **56 SQL statements**. A separate whitespace check covered this untracked template; `git diff --check` covered the tracked working diff. Source checks found exactly one Auth user insert block, no direct account/profile inserts, two fixture-trigger disable/restore cycles, no psql directives, no replication-role statement, no COMMIT, and a PASS/FAIL SELECT after ROLLBACK. An independent static review found and corrected the reused-marker false PASS risk, the initial `SELECTION` state that missed the real `ACTIVE` transition, and the missing fourth-candidate assertion. These checks do not exercise PostgreSQL behavior.

Untested branch assumptions: the SQL role can call `pg_control_system()` and `pg_catalog.hashtextextended`, insert test `auth.users` rows, and alter user triggers on the nine public tables; the Auth hook creates exactly the expected account/profile rows; the current branch schema accepts every fixture row while internal constraints remain active; MCP keeps one backend session for the whole call and returns the last SELECT; and the branch carries the exact current-schema function preimages. If any assumption fails, stop on the disposable branch and inspect it rather than weakening the guard or redirecting to DEV.
