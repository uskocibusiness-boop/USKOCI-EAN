# CCP01 — Supabase MCP branch feasibility (read-only assessment, 21 October 2026)

**Result:** A disposable Supabase branch could host an adapted CCP01 regression without local `psql`, but **the present `projection.regression.sql` cannot run unchanged through the connected MCP SQL tool**. No branch was created, no candidate SQL was applied, and no fixture or cancellation was executed in this assessment. The SQL proof remains open.

## Fresh evidence from canonical DEV

Read-only `execute_sql` on `leqcwgzvjsxugfgzdmth` found the exact two `forward.sql` predecessor MD5s: `private.need_candidate_states_v5(uuid)` = `6e9656abe2475b53b6dc49ead1131620`; `(uuid,uuid[])` = `1c25fd199f84964d2ffbb5b54d5aeca0`. Both are owned by `postgres`, `SECURITY DEFINER`, `search_path=pg_catalog`, with no `anon` or `authenticated` EXECUTE. Both public owner readers and `rpc_cancel_agreement(uuid,text)` have authenticated EXECUTE and no anon EXECUTE. Reader MD5s are `40adbec0dc31cc43f2d97bceb145334d` (whole list) and `c0165d7d2815b086ab30f032b5723eee` (page); cancellation MD5 is `ae6d54b2b643d2c972a12f651e236d11`. `list_branches` returned only default `main`. These are DEV preimages, **not branch readback**.

The connected SQL role is `postgres`. It can `SET ROLE authenticated` and `anon`, but `has_parameter_privilege(current_user,'session_replication_role','SET')` is **false**. Consequently, both `SET LOCAL session_replication_role=replica` lines in the existing proof are a hard gate unless a branch independently proves a different privilege. `auth.users` is owned by `supabase_auth_admin`, which this `postgres` role cannot act as. Its `on_uskoci_auth_user_created` trigger creates an `app_accounts` row and both REQUESTER and WORKER `app_profiles` rows. Merely deleting the replica statements therefore makes the explicit account/profile inserts in `$seed$` conflict with the trigger-created rows.

A harmless read-only MCP call containing `BEGIN; SET LOCAL application_name=...; SELECT ...; ROLLBACK; SELECT ...;` completed, and the final result had the original `application_name=mgmt-api`. This confirms multi-statement execution and local rollback in that call. It does **not** prove the adapted fixture, error-stop behavior, temporary functions, or timeout. The connector returned only the final SELECT result.

## Required adaptation on a newly identified disposable branch

1. Create the branch only after the connector's branch-cost flow is satisfied. Use the returned **branch `project_ref`**, never canonical DEV or `uskoci-v0-e2e-lab`, for every write. Confirm branch health and read back its schema/function preimages. [Supabase branches are data-less and replay migration history](https://supabase.com/docs/guides/deployment/branching); a branch can have an incomplete schema if that history differs from live main ([MIGRATIONS_FAILED guidance](https://supabase.com/docs/guides/troubleshooting/branch-in-migrations-failed-status)). Stop if either predecessor MD5 differs or required functions/tables are absent. A branch name alone is not evidence of the current DEV schema.
2. For the branch only, send the predecessor guard, both `CREATE OR REPLACE FUNCTION` bodies, and the assertion block from `forward.sql` through the DDL `apply_migration` tool. Prepare a branch-only payload without the file's outer `BEGIN`/`COMMIT` if the migration endpoint controls its own transaction; verify that behavior on the branch before relying on it. An MCP migration creates **branch migration history**. Read back both definitions, owner, `prosecdef`, `proconfig`, and effective ACLs; compare the three unchanged public RPC MD5s above. Discard the branch if application is partial or any invariant drifts.
3. Make a separate MCP regression payload from `projection.regression.sql`. Remove the psql-only `\set ON_ERROR_STOP on` and `\echo PASS ...`; keep `BEGIN` and terminal `ROLLBACK` **inside one `execute_sql` call** so `pg_temp` functions, transaction-local fixture IDs/JWT claims, role switches, and cancellation share one session. Add a final `SELECT 'PASS CCP01 ...' AS result` **after** `ROLLBACK`, because MCP returns only the last query result. First run a harmless branch-only intentional-error probe to establish that an earlier failing statement cannot still yield that final PASS marker. Never split the fixture and RPC calls across MCP requests.
4. Rewrite the fixture before sending it. The branch SQL role must not assume replica mode. A possible branch-only route is transaction-local `ALTER TABLE ... DISABLE TRIGGER USER` for the **nine public fixture tables owned by `postgres`**, then re-enable those triggers before the real `rpc_cancel_agreement` and reader calls; foreign keys remain active and must be satisfied. Leave `auth.users` triggers enabled. Let its insert hook create accounts/profiles, remove the explicit `app_accounts` inserts, and `UPDATE` the hook-created profiles by `(account_id,kind)` to the fixture UUIDs, status, city, names, and worker skills. The synthetic replacement step needs the same trigger handling. This is a new proof variant, not a verified drop-in edit; if normal Auth hooks, constraints, or permission checks change its expected rows, stop and inspect on the disposable branch rather than bypassing them silently.
5. Check branch-local function/ACL/closure snapshots **before and after** candidate application and after the proof. Record both helper definitions and their no-public-EXECUTE property; authenticated-only access to both owner readers; unchanged cancellation/worker-reader definitions; source/program closure digests, certificate row, readiness, and binding. Compare branch values to its own baseline: DEV already has a pre-existing live/certified closure mismatch (`retention_ai_source_ready()=false`, binding `null`), so equality to a presumed healthy DEV certificate is not a valid pass condition. Check that rollback left no `ccp-...@proof.invalid` users or CCP task rows, against a pre-run count. Any error, timeout, unsupported transaction control, or fixture residue means **no proof**.

This SQL variant would still prove only `3/3 → 2/3 → synthetic 3/3` projection parity. It does not call `rpc_select_response` for the replacement or perform signed HTTP/Android behavior; those remain separate gates. No branch or DEV migration should be promoted from this assessment.
