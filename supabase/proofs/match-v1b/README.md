# MATCH-V1B disposable proof

Run by `.github/workflows/match-v1b-remote-waves-proof.yml` (push to `candidate/match-v1-20261007` on these paths, or `workflow_dispatch` once the file is on the default branch). Two independent jobs, each from its own fresh chain: `remote` (behaviour) and `remote-load` (40,000 matching workers). Loopback database only; no DEV, provider, device or push. The MATCH-V1, ZONE-PERF and DISCOVERY-ZAMENE proofs have their own workflow (`supabase/proofs/match-v1/`, `supabase/proofs/zone-perf/`) and are not repeated here; this proof applies those three packages itself, in the planned order, because MATCH-V1B is a delta on top of MATCH-V1.

1. `check_source.py` — the generator is byte-exact (`build_candidate.py --check`), the MATCH-V1 files it was built against are unchanged (sha256), every SQL file, DO block and function body is parsed (pglast 8.4), the cap counts exactly the event the wave emits (`OPPORTUNITY_AVAILABLE`, normal urgency, `WORKER`, 24 hours, `limit p_cap`), the ladder statements survive in the replaced wave and the notify budget only exists inside mode ALL, the walk is a keyset walk (chunks of 500, `order by p.id`, anti-join, no sort), the configuration checker has its nine named errors and eight knobs, the remote wave checks ceiling, stop, pace and the budget before it writes a round, the premise of the budget is asserted in the chain code (the insert trigger of `notification_deliveries` takes a shared advisory lock per recipient), no `40001`, no trigger/table/index/policy statement.
2. `chain.mjs` and `fidelity.mjs` (shared with the MATCH-V1 proof) — the established disposable chain in canonical DEV order and the 23 relevant bodies equal to the captured DEV bodies (bounded relevant-body fidelity, not global DEV equivalence).
3. `common.mjs` — helpers shared by both proofs (one `psql` session per call with its own `statement_timeout`; a timeout or an error is a result, never an exception; the error keeps its head and its tail and flags `out of shared memory`).
4. `runtime.proof.mjs` (job `remote`) — real Auth + PostgREST. ZONE-PERF and MATCH-V1 are applied and the ceiling is set to 10,000 with the documented one-row update; thirty matching workers (six real ones through the product, 24 synthetic) share one unique skill so a remote task is matched by the same thirty in every state.
   - BEFORE: a task without a place goes to all thirty in ONE wave; the place-based task and the ladder are recorded as the baseline.
   - Refusals are atomic (predecessor drift, dependency drift, a stray knob, revert and switch before the apply), the preflight runs read-only and every flag is true, then MATCH-V1B is applied: exact bodies, ACL, volatility, the eight knobs merged into the row, certificate unchanged, no new `40001`, the postflight runs and every flag is true, MATCH-V1's revert refuses a foreign wave body.
   - Waves: wave 1 is the first five of the rotation (the proof sizes are 5 then 7; the real defaults 300 and 1,000 are measured by the load job), events 5 / notification rows 10, valid 24 h; an early call or a re-queued task only waits (the answer carries the time it is due); wave 2 comes through the tick after the interval with the next seven of the same rotation, no duplicate; five applications stop the waves (nothing is sent, no round is written), a withdrawn one lets them go on; an agreed or cancelled task stops for good.
   - The rotation is seeded by the task id (six tasks start at different workers), a changed profile between two waves never pulls a wave forward and the late worker is reached by a later wave, a new task revision starts the rotation again, the ceiling truncates the last wave and stops the rest (raising it continues), a physical task without coordinates is a remote task, a task with a place keeps the one wave, the keys and the global ceiling of MATCH-V1.
   - The notify budget of one transaction (budget 50, waves of 30, three tasks): the first tick sends one task, the other two are deferred (nothing written, due at once), the next ticks send them; a place-based wave of 60 workers with budget 50 goes in a chunk of the 50 nearest (the order of MATCH-V1's own function) and the rest, one per tick.
   - An empty check backs off like the tick (5, 5, 5, 8, 16 minutes); an urgent remote task uses the urgent window and ends with the urgency; one tick sends four remote tasks and the next tick finds nothing due.
   - Daily cap: a capped worker is skipped without using up a place of the ceiling and is picked up by a later wave when he has room again (never twice per revision), for remote and for place-based tasks (the next nearest takes the place); urgent events and other event types are not counted, an event older than 24 hours is not counted; the cap holds across tasks in one tick; urgent tasks ignore the cap; the default 1000 is off (a worker with 50 events is notified); the ladder is not capped; a capped worker still fits the task for the list and "Za mene".
   - Switch off: remote tasks behave exactly like MATCH-V1 mode ALL (same result keys); switch on again; a bad knob cannot be switched on. The ladder gives the same groups and result keys as before, whatever the new knobs say. Every bad or misspelt knob (22 cases, the budget included) is `DISPATCH_CONFIG_INVALID` and nothing is delivered.
   - DISCOVERY-ZAMENE applies on top and reverts, then MATCH-V1B, MATCH-V1 and ZONE-PERF are reverted in the opposite order: the catalog is exactly the one before each application, the row and the certificate are restored, a remote task goes to everyone at once again; the in-transaction artifact applies to the same catalog; DISCOVERY-ZAMENE first and MATCH-V1B second works and reverts exactly too.
5. `load.proof.mjs` (job `remote-load`) — 40,000 active workers who all do one kind of work (50 of them also a rare second kind), 8,000 with an approximate point, 3,000 draft profiles, ten events per worker (400,000 rows; about 47 % of the workers have a new-task notification from the last 24 hours) and 28 tasks as synthetic SQL rows (triggers off, labelled `V1B load`), vacuumed and analyzed. Measurements that must leave nothing behind run in ONE rolled-back transaction; the ones that need several transactions (the series of waves, the ticks, the chunks of a place-based wave) are committed and cleaned up (set-based, triggers off). Every measurement has its own `statement_timeout` (90 s; the series, the ticks and the chunks up to 170 s); a timeout or an error is recorded, a NEW measurement that does not complete fails the run.
   - MATCH-V1 alone first: the cliff (a task with a place at ceilings 2,000 / 5,000 / 10,000 and a remote task at 10,000 in ONE transaction), the rare-kind task, the place-based retrieval.
   - A `pg_locks` diagnosis of the premise (one advisory lock per notified recipient, held to the end of the transaction).
   - Then MATCH-V1B: the series 300, 1,000 x 9, 700 and the refusal, every wave in its own transaction (rows, bytes and milliseconds per wave; the late waves must cost no more than the early ones), calls per wave with `track_functions` (a wave evaluates about the workers it notifies, not the 40,000 profiles), the cap off / 3 / 1 (skipped workers never reach the prefilter), everybody at the cap (the worst case for the walk), the rare-kind task (first check, empty check, immediate third check), 25 remote tasks by ticks (first waves of 300, then second waves of 1,000: no tick may fail, notify more than the budget or take more than 40 s), the cap probe by itself (20,000 calls, the plan), the task with a place with and without the cap, and the task with a place sent to the ceiling of 10,000 in chunks of at most the budget.
   - The states are reverted exactly in the `finally` block whatever happened.

Report files in the artifact: `v1b-report.json`, `v1b-load-report.json`, `v1b-load-summary.md`, `chain-fidelity.json`, `source-check.txt`.
